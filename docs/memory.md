# 内存与缓存性能检测（`memory.*`）

[返回文档目录](README.md) | [简体中文首页](../README.zh-CN.md)

内存章节由四个共享同一套**自适应工作集规划器（Working-Set Planner）**的插件组成：
- **`memory.sysbench`**：顺序读写吞吐带宽
- **`memory.stream`**：科学计算标准 STREAM 四核函数持续内存带宽
- **`memory.latency`**：L1 / L2 / L3 各级缓存与主存随机访问延迟
- **`memory.numa`**：多路/多节点机器的跨 NUMA 节点带宽与延迟矩阵

---

## 1. 核心机制：共享工作集规划器（`Plan`）

许多简易跑分脚本使用固定大小的内存块（例如固定 `1 MiB` 或固定 `1 GiB`）：前者在大缓存服务器 CPU（如拥有 256 MiB L3 缓存的 EPYC/Xeon）上完全停留在 CPU 缓存内，测出虚高的“缓存速度”；后者在小内存 VPS 上直接引发 Swap 抖动甚至 OOM。

`lowendaff-bench` 在每个内存插件启动时动态读取当前可用内存 `A` 与 CPU 末级数据缓存总和 `C`（若虚拟化环境未暴露缓存大小，默认按 `C = 32 MiB` 估算并在报告中附注提示），遵循两条硬性准则：

1. **安全上限（绝不撑爆内存）**：任何单轮测试分配的总内存严格不超过当前可用内存的一半，即 **`预算 B = A / 2`**。
2. **穿透缓存下限（测真实主存）**：测量主存带宽或延迟时，工作集目标至少为末级缓存总量的 **4 倍（`>= 4 × C`）**。若主机内存极小导致 `4 × C > B`，规划器会按 2 的幂次逐步折半直至装入预算 `B`（不低于 4 KiB 页大小），并在报告中自动添加备注，提醒读者工作集小于 `4 × C`、部分数据可能命中缓存。

## 2. 内存顺序读写：`memory.sysbench`

| 属性 | 说明 |
|---|---|
| 插件 ID | `memory.sysbench`（所属分组：`memory`） |
| 适用平台 | 全平台 |
| 依赖工具 | 静态构建 `sysbench 1.0.20` |
| 超时上限 | `20 分钟` |

### 测试逻辑
- 依次测量 **顺序读（Read）** 与 **顺序写（Write）** 两种操作，每种操作分别运行 **单线程** 与 **全部可用线程 `N`**（单核主机仅跑 1 线程列），单轮固定时长 10 秒：
  - 单线程缓冲区大小：不小于 `4 × C` 的最小 2 的幂（超出 `B` 时折半拟合）。
  - 多线程每线程缓冲区大小：`max(1 MiB, ceil_pow2(4 × C / N))`，保证 `N` 个线程总缓冲区既穿透总末级缓存，又不超出 `B`。
- 输出单位为二进制 `MiB/s`，每轮失败最多自动重试 4 次。

## 3. 持续内存带宽：`memory.stream`

| 属性 | 说明 |
|---|---|
| 插件 ID | `memory.stream`（所属分组：`memory`） |
| 适用平台 | 全平台 |
| 依赖工具 | 预编译 6 档数组规模的静态构建 `STREAM 5.10` |
| 超时上限 | `30 分钟` |

### 测试逻辑
- 标准 STREAM 基准要求在编译期固定数组元素数量。工具包内预置了 **6 个档位**：单数组含 `2M`、`4M`、`8M`、`16M`、`32M`、`64M` 个 8 字节双精度浮点数（单数组 `16 MB` 至 `512 MB`，三数组总占用约 `48 MB` 至 `1536 MB`）。
- **自动选档**：规划器挑选满足“单数组字节数 `>= 4 × C`”的最小档位（符合 STREAM 官方运行规则）；若该档位的三数组总大小超出可用内存预算 `B`，则向下回退到能装入 `B` 的最大档位，并在报告备注中诚实声明单数组未达到末级缓存 4 倍的官方规则阈值；若连最小的 `2M` 档位（约 46 MiB）都装不下，则安全跳过并说明原因。
- 分别在 **单线程** 与 **全部可用线程** 下测量四个经典向量核函数的持续带宽（十进制 `MB/s`）：
  - `Copy`: `a(i) = b(i)`
  - `Scale`: `a(i) = q * b(i)`
  - `Add`: `a(i) = b(i) + c(i)`
  - `Triad`: `a(i) = b(i) + q * c(i)`

## 4. 缓存与主存延迟：`memory.latency`

| 属性 | 说明 |
|---|---|
| 插件 ID | `memory.latency`（所属分组：`memory`） |
| 适用平台 | 全平台 |
| 依赖工具 | 静态链接 glibc 2.41 的 `multichase` |
| 超时上限 | `20 分钟` |

### 测试逻辑
- 使用 Google `multichase` 构造随机指针追逐链表（Pointer Chasing），消除硬件顺序预取器的干扰，测量真实的逐级访存延迟（单位 `ns`）：
  - **L1 / L2 / L3 缓存行**：对内核暴露了容量的每一级数据缓存，分配**单个缓存实例容量的一半（`size / 2`）**作为追逐缓冲区，确保链表稳定驻留在目标层级内而不溢出到下一级；内核未暴露容量的缓存级别会自动略过并在备注中列出。
  - **主存行（`Memory`）**：分配与单线程 `sysbench` 相同的 `>= 4 × C` 缓冲区，使绝大多数随机跳转均穿透末级缓存直达物理内存。

## 5. 跨节点拓扑矩阵：`memory.numa`

| 属性 | 说明 |
|---|---|
| 插件 ID | `memory.numa`（所属分组：`memory`） |
| 适用平台 | 具备 **至少 2 个可用 NUMA 节点** 的多路物理机、分区大规格虚拟机或容器 |
| 依赖工具 | `multichase` 与同包的 `multiload` |
| 超时上限 | `30 分钟` |

### 测试逻辑
- **适用性判定**：结合 `/sys/devices/system/node` 与当前进程的 `Cpus_allowed_list`、`Mems_allowed_list` 亲和性掩码，统计真正可绑定线程或可分配内存的节点数；少于 2 个节点时在编排阶段直接归入 `Not applicable here`，不浪费时间。
- **二维矩阵测量**：以“运行线程的 CPU 节点”为行、“分配缓冲区的内存节点”为列，对矩阵中的每个单元 `(row, col)` 同时约束内存分配上限（不超过目标节点当前空闲内存的一半与全局预算 `B` 的较小值）：
  1. **跨节点带宽表**：使用 `multiload` 运行 `stream-triad` 负载，测量节点 `row` 上的全部可用核心访问节点 `col` 内存时的聚合带宽。
  2. **跨节点延迟表**：使用 `multichase` 测量从节点 `row` 访问节点 `col` 主存的随机指针追逐延迟，直观展现本地访存（对角线）与跨插槽互联（QPI / UPI / Infinity Fabric）的性能差距。
